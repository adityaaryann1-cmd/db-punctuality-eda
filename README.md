# Deutsche Bahn Punctuality: Exploratory Data Analysis

An independent EDA of Deutsche Bahn (German national rail) train punctuality,
covering January-July 2026. It measures how often trains actually run on
time against DB's own official punctuality definition, breaks that down by
train category, hour of day, day of week and station, and surfaces the
delay distribution rather than just the mean.

Live demo: Streamlit app reading precomputed summary tables (see "Run" below
to run it locally).

## Data source and licence

Source data: [`piebro/deutsche-bahn-data`](https://huggingface.co/datasets/piebro/deutsche-bahn-data)
on Hugging Face, sourced from Deutsche Bahn's public timetables API
(schedule, delay and cancellation data). Licensed **CC BY 4.0** (Attribution
4.0 International) by Deutsche Bahn. This project uses the monthly
processed Parquet files for 2026-01 through 2026-07 (~4GB, ~101.7M rows).

## Architecture

```
data_check.py  -->  db_data_2026/*.parquet  (raw, gitignored, ~4GB)
eda_pipeline.py -->  DuckDB queries the raw Parquet directly  -->  eda_results/*.parquet (small summaries)
app.py         -->  Streamlit reads only eda_results/, never the raw files
```

**Why DuckDB queries Parquet directly instead of loading into Pandas:** the
raw data is ~101.7 million rows across 7 files, too large to comfortably fit
and manipulate in memory as a Pandas DataFrame on a laptop. DuckDB executes
SQL directly against Parquet files out-of-core (reading and processing in
batches, not loading the whole dataset into RAM), so aggregation happens
without ever materializing the full dataset as a Python object.

**Why aggregates are precomputed for the serving layer:** the Streamlit app
is what recruiters and hiring managers actually open. If it queried the raw
Parquet files on every page load, cold start would mean scanning 4GB before
the first chart renders. Instead, `eda_pipeline.py` does that scan once
offline and writes small (a few KB) summary Parquet files; the app only ever
reads those, so it starts instantly regardless of raw data size.

## Setup and run

```bash
python -m venv venv
source venv/bin/activate            # Windows: venv\Scripts\activate
pip install -r requirements.txt

python data_check.py                # downloads db_data_2026/*.parquet (~4GB) and sanity-checks it
python eda_pipeline.py              # aggregates raw data into eda_results/*.parquet + run_metadata.json
streamlit run app.py                # serves the dashboard from eda_results/ only
```

## Dataset scale

From `eda_results/run_metadata.json`, generated by the pipeline itself:

- 101,702,091 total scheduled train movements
- 97,270,559 operated (non-cancelled) trains
- 4,431,532 cancelled trains
- 5,379 distinct stations
- 100 distinct train_type codes in the raw data (dashboard breakdowns are
  restricted to the 6 passenger categories in `config.TRAIN_TYPE_WHITELIST`)
- Date range: 2026-01-01 to 2026-07-31
- 7 monthly source files

## Key findings

- **Overall delay rate: 15.1%** of operated trains arrived/departed ≥6
  minutes late (DB's own punctuality threshold), out of 97,270,559 trains
  that actually ran. This is the corrected figure — see "denominator note"
  below.
- **ICE (long-distance) trains are the least punctual**, delayed 44.4% of
  the time, followed by EC (43.6%) and IC (40.8%). Regional/S-Bahn services
  are far more reliable: RE 23.0%, RB 13.4%, S-Bahn 11.9%.
- **IC has the highest cancellation rate** among the major categories at
  9.8%, versus 3.5% for RE and RB.
- **The mean understates the worst case.** EC's mean delay is 13.7 minutes,
  but its 99th-percentile delay is 138 minutes — over 2 hours worse than the
  average suggests.
- **Delays are a weekday problem.** Weekday delay rates cluster around
  15.6-16.8%, dropping to 12.3% on Saturday and 9.8% on Sunday, consistent
  with weekday commuter and freight-path congestion.

## Denominator note (why the rate below is different from a naive one)

The raw data counts a cancelled train's `delay_in_min` as unset/not
applicable to delay, but a naive query using `COUNT(*)` as the denominator
for delay rate would still include cancelled trains in that denominator,
silently understating the true delay rate among trains that ran. This
project explicitly separates:

- **scheduled movements** (`COUNT(*)`, includes cancellations)
- **operated trains** (`is_canceled = False`) — the correct denominator for
  any delay rate
- **cancelled trains** — reported as its own rate, never folded into "on
  time"

Every delay-rate metric and label in the app states this explicitly.

## Limitations and next steps

- Percentiles and delay rates in `by_type`/`by_hour` use exact
  `PERCENTILE_CONT`, which requires a full sort per group; this is fine at
  the current data volume (runs in seconds) but would need approximation
  (`approx_quantile`) at much larger scale.
- `departure_planned_time` is NULL for ~7.6M rows (a train's final stop on
  its line has no further departure), so the by-hour breakdown implicitly
  excludes those rows; day-of-week uses the `time` column instead, which is
  always populated, to avoid the same gap.
- `delay_in_min` contains a small number of extreme outliers (observed range
  roughly -1446 to +1439 minutes), some suspiciously close to exactly ±24
  hours, suggesting a handful of source-data timestamp/date-rollover errors
  rather than genuine day-long delays. These were not filtered out, so they
  can pull group means (though not medians) slightly.
- Station names are free text from the source API and are not deduplicated
  against a canonical station registry, so near-duplicate station name
  variants may be undercounted individually.
- The dataset only covers Jan-Jul 2026, so no year-over-year or seasonal
  (e.g. winter weather) comparison is possible yet; adding prior years would
  be the natural next step.
